**The `getAssets` hook** (core ≥ 4.13.0, from `@nera-static/core`'s
`src/setup-plugins.js` and its design notes — confirm against
`node_modules/@nera-static/core/src/setup-plugins.js`, `src/render.js`
`copyPluginAssets`, and `src/index.js`):

- `export function getAssets({ app, pagesData })` returns an array
  `[{ from, to }]`. `from` is an **absolute** path to a file or a folder. `to` is
  a path **relative to `public/`**.
  - For a **file** entry, `to` is the target *file* path
    (`{ from: '/abs/x/tutorials.json', to: 'tutorials.json' }`).
  - For a **folder** entry, `to` is the folder its *contents* go into (`''` means
    `public/` itself; a file entry with `to: ''` is skipped with a warning).
- It runs **after every plugin's `getAppData`/`getMetaData`**, in plugin order,
  with the **final** `app` and `pagesData` — so a plugin sees the data its own
  `getAppData` produced (e.g. `app.tutorials`).
- Core copies the entries **after the theme's assets and before the site's**:
  theme → plugins → site, so a file in the site's own `theme/assets/` wins a
  name clash. No `.neraignore` filtering. The copy happens **before** `base_path`
  rewriting and `asset_hashing`, so both cover plugin files.
- **Why it exists:** plugins run before core deletes and re-creates `public/`
  (stage order: load app → pages → plugins → render, and render starts with
  `deleteFolder(public)`). A file a plugin writes into `public/` directly is
  lost. Write into **`.nera-cache/<plugin>/`** instead — `nera new` git-ignores
  `.nera-cache` (its `.gitignore` lists it; this repo's `.gitignore` does too) —
  and return it from `getAssets`. This is what `plugins/llms-txt` and
  `plugins/skill-zip` do.
- **Warnings, not errors:** a non-array result →
  `⚠️ Plugin "<name>" getAssets returned invalid format, skipping.`; a bad entry
  (missing/relative `from`, missing `to`, absolute `to`, `to` escaping `public/`)
  → `⚠️ Plugin "<name>" getAssets entry skipped: <reason>`; a `from` that does not
  exist is skipped at copy time with a warning. A `getAssets` that **throws**
  fails the build (like a throwing `getAppData`).
- The other two hooks: `getAppData` must return a plain object, else
  `⚠️ Plugin "<name>" getAppData returned invalid format, skipping replace.` and
  the old `app` is kept; `getMetaData` must return an array, else
  `⚠️ Plugin "<name>" getMetaData returned invalid format, skipping append.` —
  so "check the console when a plugin does nothing". Copy these strings from the
  installed core, not from this brief, if you quote them.

**Synchronous hooks.** All hooks have been **awaited since core 4.3.0**. Before
that, an `async getAppData` silently replaced `app` with a Promise. Every site on
`@nera-static/nera` runs a core far above 4.3.0, so an async hook works today;
synchronous stays the **safe default** (and is what the published plugins do).
Reword the current "Keep them synchronous — an async hook can silently wipe `app`
on older generator versions" so it is accurate on both counts. Do not claim
async is broken.

**Local plugin folder.** Core's default for local plugins is
`src/plugins/<name>/index.js`; `folders.plugins` in `config/app.yaml` changes it
(this site sets `./plugins`). A site from `npx @nera-static/nera new` has no
`folders.plugins` key, so the default applies — confirm that in the throwaway
site by putting the plugin in `src/plugins/` and seeing it load
(`✅ Loaded local plugin: tutorials-list` in the build log).

**The simplified `tutorials-list`.** The site's real plugin
(`plugins/tutorials-list/index.js`) matches on `meta.dirname` (any language
prefix) and adds `lang`; the tutorial's simplified version matches
`href.startsWith('/tutorials/')`. Simplified is fine as long as it works in the
throwaway site and the text calls it simplified. Keep it unless it is wrong.
